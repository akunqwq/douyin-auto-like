# 抖音自动点赞

一个用于网页版抖音的 Tampermonkey 用户脚本，视频播放后延迟 10 秒，通过 Z 键通道自动点赞，并自动跳过已点赞的视频。

## 特性

- 自动点赞当前正在观看的未点赞视频，覆盖推荐流、搜索结果、精选、播放页等页面。
- 延迟 10 秒再点赞：刷到不喜欢的视频可以直接划走，不会立刻被点赞；视频时长不足 10 秒的，阈值自动降至 3 秒，避免短视频播完还没轮到点赞。
- 已点赞的视频直接跳过（`data-e2e-state` 确认为已赞），不会误取消赞。
- 通过 Z 键事件触发点赞，与抖音页面自身的快捷键通道一致；结果由 `data-e2e-state` 迁移确认，只认这一个权威信号。
- 检测到手动取消点赞后不再干预该视频；滑走再滑回视为新的观看过程。
- 本次页面加载内，同一个视频只触发一次点赞。
- 今日记录按天保存：跨页面刷新保留，跨天自动清零，存储里只留一天。
- 可将今日刷到的视频 ID 导出为 JSON，方便回看。
- 悬浮面板默认收起为入口；长按入口展开完整面板，点 X 收起，不遮挡页面。


## 导出今日记录

Tampermonkey 菜单 →「导出今日刷视频数据」，会下载 `douyin_video_ids_YYYY-MM-DD.json`，内容形如：

```json
{
  "date": "2026-11-02",
  "total": 2,
  "ids": [
    "7xxxxxxxxxxxxxxxxxx",
    "7yyyyyyyyyyyyyyyyyy"
  ]
}
```

`id` 唯一取自视频自身祖先链上的 `data-e2e-vid`，通常落在 `feed-active-video` 或弹层容器上。

## 计数口径与手动取消点赞

面板上的「今日累计刷视频 N」统计的是**今日被脚本识别为当前观看对象的视频数量**，与是否点赞无关。

- 在当前视频上手动取消点赞后，脚本不会再对它出手，除非你滑走又滑回来，那算一次新的观看。
- 取消之后不会自动补赞，省得跟你的手动操作打架。

## 实现要点

### 识别：多级证据解析器

`getCurrentVideo()` 按证据可信度从高到低试三层 resolver：

1. **平台标记**：抖音用 `feed-active-video` 自行标记当前视频。精选弹层页上平台会同时标记背景视频和弹层视频，最后靠"在播优先 + 可见面积"裁决。
2. **URL 匹配**：`modal_id` 和 DOM 节点 vid 精确一致才采信；dialog 里的候选还得和 `modal_id` 身份对得上，对不上就放弃。
3. **属性启发**：可见 + 在播 + 操作栏佐证，兜底用。

身份纪律只有一条：视频 ID 只出自平台 DOM 标记，也就是视频自身祖先的 `data-e2e-vid`。`modal_id` 是 URL 上的身份标识，只做精确匹配和一致性校验，不给身份不明的视频兜底。resolver 只负责找两种身份的对应关系，不负责制造对应关系。

### 预览视频守卫

浏览页 hover 预览视频可能"在播 + 大尺寸"，仅靠 vid 祖先可能误判为当前视频。兜底路径要求容器内存在操作栏元素（`video-play-more`，实测：播放态容器有、预览容器无）才采信。

### 触发：延迟 + 到点重校验

排程时不置"已触发"，计时器到点才重新校验：还是不是同一视频、脚本有没有被关、视频还在不在播、赞还在不在，任一不满足就放弃。默认延迟 10 秒；视频时长不足 10 秒时降到 3 秒，不然短视频都播完了，计时器还没响（`duration` 为 NaN 或 Infinity 时回落默认阈值）。

标签页切到后台时，倒计时冻结而不是继续走：隐藏瞬间清掉计时器并记下剩余毫秒，切回前台按剩余时间重排。后台期间既不消耗等待进度，也不会发出点赞——10 秒延迟的前提是"你在看"。

Z 键发出去之后到底点没点上，要看 `data-e2e-state` 有没有从未赞变已赞；区分"没生效"和"用户取消"，靠的是 `autoLikeRequested / autoLiked` 状态机，不是靠猜回读时序。

### 人工否决规则：仅当前停留生效

手动取消点赞只否决当前这次停留。滑走后旧会话（含计时器、否决标记）被清理，滑回同一视频视为新观看，允许重新排程点赞。

## 播放定时器

面板选择时长（10 / 15 / 30 / 45 / 60 分钟）后启动，到点暂停**当时**正在播放的视频。一次性，结束后不再干预，手动恢复播放由使用者决定。

### 设计决策

- **独立于点赞通道**：定时器不读写 `running`、`session`、`frozenRemaining`。现有 `onVisibilityChange` 的语义是「后台冻结点赞倒计时」，睡眠定时是墙钟时间，两者相反，挂在一起会被冻结逻辑吞掉；`pause` 事件还会触发 `process()`，所以定时器使用独立状态节点，不复用 `setStatus()`。
- **不缓存视频引用**：启动时只记 `playbackEndAt = Date.now() + duration`，到期重新调用 `getCurrentVideo()`。设置期间可能已刷过几十条视频，缓存引用会指向过期 DOM。
- **沿用 A 口径，识别失败就不动**：`getCurrentVideo()` 返回的是点赞上下文 `{id, video, likeButton}`，`getVideoContext()` 把 `data-e2e-vid` 合法性作为硬门槛。曾考虑拆出纯视频定位函数，已否决：`resolveUrlMatchedVideo()` 依赖 `modal_id` 身份匹配来定位主视频，`resolveHeuristicVideo()` 把 id 校验与预览守卫绑在同一次调用里，抽掉 id 会改变裁决口径、退回宽松识别，与「宁可不暂停也不错暂停」冲突。代价是暂停成功率受限于身份识别成功率，三级 resolver 全失败时显示「未能定位当前视频」。
- **`pause()` 不检查 `running`**：自动点赞开关只管点赞通道，`video.pause()` 作用于 HTMLMediaElement，与点赞开关状态无关。
- **不抽统一控制层**：两个功能只共享「定位当前视频」，抽公共层的收益低于维护成本。等出现第三个独立控制功能再考虑。

### 已知限制：后台节流

| 场景 | 行为 |
| --- | --- |
| 前台刷抖音 | 正常到点暂停 |
| 后台听抖音 | 尽可能按时暂停 |
| 后台计时被延迟 | 回前台按 `playbackEndAt` 立即补判 |
| 页面被关闭 | 不保证继续执行，`endAt` 不持久化 |

现象：标签页在后台时 `setTimeout` 被降频，到点回调可能迟到。根因：浏览器后台节流策略，不是脚本计时错误——剩余时间始终由 `Date.now()` 与 `endAt` 的差值计算，不会随降频而漂移。验证方式：设一个短时长后切走标签页，超时后切回，观察是否立即暂停。

第一版刻意只采用 `endAt + setTimeout + visibilitychange`，不引入 Web Worker 或额外后台架构。这是浏览器环境限制，不作为功能缺陷处理。收起态不显示倒计时，剩余时间只在长按展开后的面板里可见。

## 已知限制：不支持抖音页面内小窗

目前脚本面向抖音网页版的推荐流、搜索结果、精选、播放页等常规页面，抖音页面内的小窗模式尚未适配。

### 调查记录

拿 devtools 看过，记录如下：

- 小窗窗口的 URL 为 `about:blank`，`window === window.top` 为 `true`，且 `window.opener` 存在并可以访问原始抖音页面。
- 正常推荐流中的视频位于 `[data-e2e="feed-active-video"]` 容器内，并可读取 `data-e2e-vid`。
- 搜索结果页点开视频后，活动项位于 `[data-e2e="modal-video-container"]` 内（`id="dy-modal-video-container-search_multi_modal"`）。此时页面上会有 2 个 `feed-active-video`（背景推荐流 + 浮层），脚本取浮层内的那个。
- 抖音精选页的活动项位于 `[data-e2e="slideList"]` 内。
- 点赞按钮为 `[data-e2e="video-player-digg"]`，未赞 `data-e2e-state="video-player-no-digged"`，已赞 `data-e2e-state="video-player-is-digged"`。已赞时按钮会额外带上构建生成的 class（如 `Fw5w6T_O`），会随发版变化，不可用于判断。
- 播放器 class 不可靠：暂停时 `xgplayer-playing` 依然存在，会与 `xgplayer-pause`、`xgplayer-inactive` 同时出现，不能作为「正在播放」的依据。
- 曾考虑 `[data-e2e="video-info"]` 的 `data-e2e-aweme-id` 与 URL `modal_id` 作为视频 id 的备用来源，已否决：id 只出自视频祖先链的 `data-e2e-vid`，modal_id 仅用于匹配与一致性校验。理由：防止 URL 身份与 DOM 身份错配，宁可不点、不可错点。
- 进入小窗后，该容器在小窗文档中不存在，视频位于 `xg-video-container` 内。
- 正常推荐流与小窗中观察到相同的 `data-xgplayerid`、`blob:` 媒体地址和视频时长。这些现象提示播放器或媒体状态可能具有连续性，但尚不足以证明底层播放器实例始终相同。
- 当前小窗文档中没有脚本的悬浮面板。现有脚本使用的 `@match https://www.douyin.com/*` 不匹配 `about:blank`，所以脚本不一定会自动在小窗里跑起来。

### 暂不适配的原因

现有实现依赖正常推荐流的活动视频容器和相关视频标识。小窗具有独立的文档上下文，DOM 结构也不同。仅修改视频选择器不足以保证倒计时连续、视频去重和点赞状态判断正确。

所以当前版本不支持小窗。正常推荐流不受影响。

以上结论来自特定浏览器环境下的控制台观察，不代表抖音所有版本和小窗实现均具有完全相同的内部结构。
